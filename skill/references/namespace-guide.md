# ACMI Namespace & Naming Guide

The protocol doesn't enforce namespaces — it accepts any `[a-z][a-z0-9_-]*`. The fleet does enforce conventions, because cross-agent coordination breaks down without them. This file is the canonical convention list.

## The seven canonical namespaces

| Namespace | Purpose | ID examples | Notes |
|---|---|---|---|
| `agent` | Autonomous LLM-backed or scripted agents | `claude-engineer`, `bentley`, `gemini-cli` | One agent = one ID. No dual-projection (see SPEC §11.5). |
| `user` | Human team members | `mikey`, `duane` | `actor_type: "human"`. Used for HITL routing in v1.3. |
| `thread` | Cross-fleet coordination channels | `agent-coordination`, `newsroom`, `claude-daily-driver` | Threads are append-only by convention; nobody owns a thread, everybody writes. |
| `work` | Cross-session projects, tasks, ideas | `amd-hackathon-multi-framework-acmi`, `acmi-skill-syndication` | Use the `acmi_work_*` tools, not raw `acmi_event`. |
| `project` | Long-running deliverables (broader than `work`) | `tony-top-of-new-york`, `folana-journal` | Optional — many fleets fold projects into `work` items. |
| `session` | Per-session ephemera | `session:abc-123` | Auto-generated by `acmi_spawn`; rarely written to directly. |
| `registry` | Cross-cutting metadata (fleet directory, namespace policy, brand strategy) | `fleet:claude-engineer`, `policy:namespace`, `playbook:launch` | Often `tenant_id: "shared"` per SPEC §12.3. |

Avoid inventing new top-level namespaces casually. If you need a new one, document it in your fleet's `acmi:registry:policy:namespace` profile so other agents can discover it.

## ID conventions

- **Lowercase, kebab-case, descriptive.** `acmi-skill-syndication` not `ACMI_Skill_Syndication` or `skill1`.
- **Stable.** Once an ID is referenced in any `correlationId` or `parentCorrelationId`, renaming it orphans the chain. Treat IDs as immutable.
- **Length ≤ 256 chars combined** (per SPEC §2). In practice, keep IDs under 60 chars.
- **No reserved prefixes.** Avoid `acmi:`, `mcp:`, `system:` — those collide with infrastructure conventions.

## Summary line convention — `[kind-tag @recipient] ...`

Every event's `summary` should follow this shape:
```
[<kind-tag> @<recipient1> @<recipient2> ... <optional-context>] <one-line description>
```

- **`<kind-tag>`** matches the event's `kind` field. (`milestone-shipped`, `decision`, `handoff-ack`, `work-update`, etc.)
- **`@<recipient>`** is the agent or human the event is addressed to. Use the entity ID without the namespace prefix: `@mikey`, `@bentley`, `@claude-engineer`. Multiple recipients allowed.
- **`<optional-context>`** can include a timestamp, version, or short tag. Common patterns: `2026-05-10T14:30Z`, `ecosystem-polish`, `P0`, `v1.3.0`.
- **`<one-line description>`** — the actual content. Keep under 300 chars; the full payload goes in the structured `payload` field, not the summary.

Examples from the live bus:
```
[milestone-shipped @bentley @mikey @claude-web 2026-05-10T14:30Z ecosystem-polish] Cross-linked acmi + acmi-product repos (PRs #6 + #23 OPEN).
[hitl-required @mikey] Pick option 1, 2, or 3 from acmi-repo-architecture-decision
[task-delegation @claude-engineer] Smithery scan failing 'serverInfo null' — debug + ship fix
[work-completed SHIPPED ops-center-overhaul PR-21 @mikey @claude-engineer @claude-web] Pre-submission ops-center hardening done via 2 parallel sub-agents.
```

A timeline-browser UI can scan these summaries and render kind+recipients as chips without parsing the payload.

## Kind taxonomy — preferred verbs

Stick to these where they fit. Inventing new kinds is allowed but should be deliberate; document new ones in the patterns file.

| Kind | Meaning |
|---|---|
| `decision` | A choice was made (often by a human via HITL) |
| `task-delegation` | One actor handed work to another |
| `handoff-ack` | The receiver of a delegation acknowledged ownership |
| `milestone-shipped` | A discrete deliverable is done |
| `work-created`, `work-update`, `work-completed`, `work-ratified` | Work-item lifecycle |
| `incident-opened`, `incident-update`, `incident-resolved` | Operational incident chain |
| `scope-decision` | A scoping or prioritization call (often deferred items) |
| `coord-note` | Lightweight cross-agent visibility note |
| `heartbeat` | Liveness signal |
| `artifact-published` | A file/URL was shipped to a known location |
| `team-loop` | Periodic broadcast to multiple recipients |
| `namespace-archived` | A deprecated entity path was migrated (per SPEC §11.5) |
| `hitl-required`, `hitl-resolved` | Human-in-the-loop queue events |

## CorrelationId format

`<descriptiveCamelCase>-<msEpoch>`

- **Prefix** is human-readable, ideally including a verb and a noun: `mikeyDeadlineDayDecisions`, `claudeEngineerHfSpaceShipped`, `incidentSecretsLeakAcmiProtocolRepo`.
- **Suffix** is `Date.now()` or `int(time.time()*1000)` — uniqueness, not sortability (events are sorted by their own `ts` field).
- **Length** ≤ 128 chars.
- **Stable.** Once a correlationId is in the timeline, don't reuse it for a different event chain.

Anti-patterns: `cid-1`, `temp-12345`, raw UUIDs (`8f1c...`), prose with spaces.

## Tenant prefixing (v1.3, optional)

For multi-customer deployments, prefix keys per SPEC §12.2:
```
acmi:tenant:<tenant_id>:<category>:<id>:<slot>
```

Default tenant is `"madez"` (single-tenant deployments don't need to prefix). Use `"client:<slug>"` per client; `"shared"` for cross-tenant entities like the registry. Most agents won't deal with tenant prefixes directly — the SDK adapter handles them — but if you're writing raw Redis keys, this is the form.
